# 계약 Contract 스윕 — 1~2단계

문서 사이의 경계를 빠짐없이 모으고 상태를 가르는 절차. 이 산출이 문서 전체의 수치 기반이
되므로, 여기서 하나 빠지면 뒤의 Layer 구조와 역산이 같이 틀어진다.

## 무엇을 Contract 로 인정하는가

**두 Workstream 이 합의해야 하는 지점**이다. 판정 기준 하나로 요약하면 이렇다.

> 이것이 정해지지 않은 상태에서 양쪽이 각자 만들면, 둘 중 하나는 버려진다.

그래서 합의 대상은 대체로 이 넷 중 하나다.

| 축 | 예 |
|---|---|
| **데이터** | 필드 집합 · 스키마 소유자 · 변환 위치 · 보존 필수 플래그 |
| **상태** | 세션·인증 모델 · 컨텍스트 주입 경로 · 캐시 소유 계층 |
| **프로토콜** | 호출 통로 단일화 · 헤더 규약 · 실행 순서 · 마운트 시점 |
| **실패 거동** | 에러 경계 소유자 · 타임아웃 · 부분 실패 격하 · 재시도 |

**Contract 가 아닌 것.** 한 Workstream 안에서만 결정되는 구현 선택(라이브러리 고르기, 폴더 구조),
그리고 이미 외부로 이관된 항목(다른 팀 소관으로 명시된 것). 후자는 Contract 로 세지 말고
**확인 요청**으로 따로 모은다 — 답이 오지 않아도 착수는 되기 때문이다.

### Contract 하나의 단위 — **문서가 스스로 가른 것은 Contract 를 가른다**

무엇을 인정하는가와 별개로 **하나로 셀 단위**를 정해야 한다. 정하지 않으면 같은 문서가 판마다
다른 수로 세어지고, **Contract 수를 입력으로 쓰는 것이 전부 흔들린다**(파트 1 부담 수치 · 파트 5
구간 수 · 판 사이 비교).

> **규칙**: 원문이 **스스로 번호·ID·표 행·불릿으로 가른 것**은 Contract 를 가른다. 그 원소들이
> 한 절에 있고 성격이 비슷하다는 이유로 **하나로 접지 않는다.**

**가르는 신호 넷** — 하나라도 있으면 원소마다 Contract 다.

| 신호 | 예 |
|---|---|
| 원문이 **번호를 붙였다** | 정책 15영역 · Must 7항목 · Could 5건 · 완료 기준 ①~⑥ |
| **ID 가 다르다** | `REQ-ENTRY-004` 와 `REQ-ENTRY-005` 는 두 자리다 |
| **표의 행이 다르다** | 보존 필수 5필드는 다섯 행이고 다섯 자리다 |
| **소유자·기한·판정이 원소마다 갈릴 수 있다** | 15영역 중 셋만 다른 Workstream 소관이면 그 셋은 따로 닫힌다 |

**실측이 이 규칙의 근거다.** 한 집합의 Contract 수가 직전 판 대비 **−33.6%** 로 떨어져 발견 하한
게이트가 처음 발동했는데, 원인이 발견 감소가 아니라 **묶음**이었다 — 원소 3개 이상을 인용한
Contract 19개 중 **일곱 자리**가 원문이 스스로 가른 것을 하나로 접은 것이었고 원소 단위로 펴면
**+32**(77 → 약 109)였다. 그리고 **묶음이 실제로 발견을 깎았다** — ①검토자가 낸 14건 중 **다섯이
「인용한 원문 표에서 원소를 흘린 자리」**다(원문 다섯 필드 중 넷만 적고 하나를 빠뜨렸다)
②검토자가 그 묶음 하나의 15영역 중 셋을 짚자 **그 Contract 가 셋으로 쪼개졌다** — 단위가 문서의
경계보다 굵었다는 것이 반영 과정에서 실증됐다.

**묶어도 되는 자리는 하나뿐이고, 묶었으면 그 사실을 적는다.** 원소들이 **같은 결정 하나**로
동시에 닫히고 참여자·강도·상태·확정 대상이 **전부 같을 때**만 한 Contract 다. 그때는 카드 근거에
**묶은 원소를 열거하고 수를 적는다** — *"원소 5개를 하나로 묶었다(`clrncYn`·`useYn`·`dispYn`·
`sortNo`·`regDt`)"*. 스무 개를 넘으면 그 표를 가리킨다(처방 ㊱ 과 같은 형식이다).

**끝낼 때 묶은 자리를 세어 `eval_metadata.json` 에 적는다** — *"원소 3개 이상을 인용한 Contract
N개 중 묶은 자리 M개(ID 열거) · 원소 단위로 펴면 +K"*. **이 수가 없으면 다음 판이 Contract 수를
같은 단위로 비교할 수 없다.**

🔴 **앞의 N 은 손으로 세지 않는다 — 스크립트가 낸다.**

```bash
python3 scripts/contract_matrix.py contracts.json      # 「원소 여럿을 인용한 Contract」 절
```

그 절이 **수와 대상 ID 를 표로 준다.** 자기 보고에는 **그 출력 줄을 그대로 붙이고**(㊱-b) 표에
오른 Contract 마다 *「접었는가」*를 갈라 적는다. **접지 않았으면 그것도 적는다** — 그 절은 세기만
하고 판정하지 않는다.

**실측이 이 지시의 근거다** — 이 수를 자기 보고로만 요구했더니 **세 산출물이 `0` 을 적었고 실측은
16·92·120** 이었다(접은 자리도 0 이 아니었다). **그 수의 정의가 어디에도 없어서** 채점자 넷의 값도
서로 갈렸다(9·16·92·120). **`0` 은 형식상 유효한 값이라 「세지 않았다」와 구별되지 않는다** —
그래서 세는 일을 스크립트로 옮겼다. 스크립트가 **어떤 표기를 보는지 출력에 찍으므로**(표 행 ·
번호·불릿 · ID · 인용 안 구분자 열거) **그 밖의 형태는 여전히 손으로 본다.**

### 한 문서 안의 모순도 Contract 가다

*"두 Workstream 이 합의해야 하는 지점"* 이라는 정의를 **문서 두 개로만 읽으면 절반을 놓친다.**
같은 문서의 다른 절이 서로 다른 값을 말하면 그것도 결정이 필요한 지점이고, 정해지지 않은
상태로 양쪽을 각자 구현하면 하나는 버려진다.

실제로 이것을 놓쳐서 채점에서 떨어진 적이 있다. **한 집합의 실패 5건이 전부 이 유형**이었다.

| 모양 | 예 |
|---|---|
| 본문과 **요약·범위 절**이 다르다 | 기능 요구사항 절에는 없는 *"5초 표시 후 리다이렉트"* 가 MVP 범위 절에만 있다 |
| 본문과 **자기 변경 이력**이 다르다 | 본문은 `1x~3x` 인데 변경 이력이 *"줌 범위(0.5x~3x) 명시"* 라고 적었다 |
| **개요 절과 상세 절**의 수가 다르다 | 모듈 개요는 *"8단계 상태 관리"*, 상세 절은 *"9단계 Flow"* 이고 표에 9개가 있다 |
| 같은 말이 **다른 것**을 가리킨다 | 인증 세션(16시간)과 업무 세션(첫 주문~종료)이 둘 다 "세션" 이다 |
| 대칭이어야 할 것이 **한쪽만** 있다 | 관리자 비밀번호는 해싱 방식이 명시됐고 단말 비밀번호는 *"로컬 저장"* 뿐이다 |

**찾는 방법.** 문서 하나를 읽을 때 세 자리를 서로 대조한다 — **개요·요약 절 / 상세 절 /
변경 이력**. 셋이 같은 수와 같은 값을 말하는지 본다. 그리고 **같은 낱말이 두 절에서 다른
대상을 가리키는지** 본다(세션·대시보드·진행률처럼 흔한 말이 위험하다).

**읽기만으로는 잡히지 않는다 — 기계로 후보를 먼저 좁힌다.** 위 문단이 '대시보드' 를
**낱말째로 적어 두었는데도** 다음 평가에서 그 낱말의 충돌을 놓쳤다. 지시를 더 쓰는 것으로는
해결되지 않는 유형이므로 목록을 강제한다.

```bash
python3 scripts/term_sweep.py <입력 디렉터리>
```

`number`(같은 단위 다른 값) · `format`(같은 접두 다른 식별자 형식) · `term`(같은 낱말 다른
대상) 세 축이 나온다. 위 표의 다섯 모양 중 **셋째·넷째·다섯째가 이 스크립트에 잡힌다.**
첫째·둘째(본문 vs 요약·변경 이력)는 절 위치를 봐야 하므로 여전히 사람이 읽는다.

참여자 표기는 **그 문서를 한 번만** 적지 않는다 — 절이 다르므로 `REQ §4.1` 과
`REQ FR-M3-04-4` 처럼 절까지 적어야 무엇과 무엇이 어긋났는지 남는다.

### 제약 문장을 목록으로 먼저 뽑는다 — 그다음 쌍별로 대조한다

위 다섯 모양을 **알고 있어도 못 찾는다.** 평가에서 이 절을 그대로 읽은 에이전트가 양립 불가
5건을 통째로 놓쳤고, 같은 원문을 받은 검토자가 **제약 문장 26개를 먼저 목록으로 만든 뒤**
쌍별로 대조해서 5건을 전부 찾았다. 차이는 지식이 아니라 **목록화**다.

읽으면서 판단하려 하면 절을 넘어갈 때마다 앞 절의 제약이 흐려진다. 목록을 손에 들고 있으면
쌍별 대조가 기계적인 일이 된다.

**그 목록과 대조표는 `notes.md` 에 쓴다 — 응답 본문에 만들지 않는다.** 문장이 수십 개면 표가
길어지고, 실측에서 **런 하나가 바로 이 자리에서 출력 한도로 죽었다**(제약 문장 쌍별 대조 중).
파일에 쓰면 도구 호출이라 한도에 걸리지 않고, 기각한 쌍의 이유까지 근거로 남는다.

**1단계 — 제약을 세우는 문장만 뽑아 표로 만든다.** 표지가 되는 말이 있다.

> *"~만 가능"* · *"~에서만"* · *"불가"* · *"필수"* · *"자동"* · *"수동"* ·
> *"자유 입력"* · *"텍스트 직접 입력"* · *"독립적으로"* · *"단일"* · *"복수"* · *"읽기 전용"*

| 출처 | 제약 |
|---|---|
| `REQ FR-M3-01-3-3` | "Plan에 연결 또는 독립 실행 가능" |
| `REQ FR-M3-01-2` | "Cycle 상태는 Test Plan 상세 화면에서만 변경할 수 있다" |

**2단계 — 쌍별로 대조한다.** 양립하지 않는 네 모양이다.

| 모양 | 실제로 잡힌 예 |
|---|---|
| A 가 허용하는 것을 B 가 **금지**한다 | *"독립 실행 가능"* ↔ *"상태 변경은 Plan 상세에서만"* → 독립 Cycle 은 상태를 바꿀 화면이 없어 영구 '준비중' |
| A 가 **자유 형식**인데 B 가 그 값을 **정형으로 소비**한다 | 결함 MSA *"텍스트 직접 입력"* ↔ M5 *"서비스별 누적 막대"* |
| **하나를 담는 자리**에 여럿이 들어온다 | 테스트 결과 *"드롭다운 단일값"* ↔ 같은 TC 가 복수 Cycle 에서 실행 + *"재실행 이력 누적"* |
| **독립 관리**한다면서 표시는 하나뿐이다 | *"상태는 Plan 단위로 독립 관리"* ↔ 카드·필터가 단일 상태만 표시 |

**셋째·넷째를 특히 본다.** 데이터 모델의 양립 불가는 요구사항 정의서와 화면 설계서에 나뉘어
적혀 있어서 한쪽만 읽으면 안 보인다. 그리고 이 넷은 **정책 문장과 화면 예시 사이**에서 가장
자주 나온다 — 정책은 *"수정 불가"* 라고 적혀 있는데 화면 목업이 *"김테스터 외 2명"* 을
보여주는 식이다.

**이 유형은 수를 고르면 끝나는 받아올 것 없는 항목이 아니다.** 상태의 카디널리티나 결과의 저장 위치를
정하는 일이라 스키마가 걸린다. 계약 구간의 **난이도를 올리는** 항목으로 따로 표시한다.

## 스윕 절차

1. **문서마다 절 목록을 먼저 뽑는다.** 절 수를 세어 표로 남긴다. 나중에 "전수 조사했다" 는
   말의 근거가 이 표다
2. **절을 순서대로 읽으며 후보를 적는다.** 이때 Contract 하나에 여러 문서의 주장이 붙는다 —
   문서별로 모으지 말고 **Contract 별로 모은다**. 같은 것을 두 문서가 다르게 말하는 순간이
   충돌이고, 그건 Contract 단위로만 보인다
3. **"미확인 · 확인 필요 · 미정" 표를 특별히 본다.** 계획서는 미결을 뒤쪽 표에 몰아 두는
   습관이 있고, 그 표가 Contract 의 절반을 담고 있을 때가 많다
4. **완료 기준·인수 조건 절을 본다.** 여기서 역방향 의존이 나온다 — A의 완료 기준 문장이
   B의 산출물을 가리키면 그 자리가 Contract 가다. **완료 기준을 항목별로 쪼개서** 각 항목이
   무엇을 전제하는지 적는다. 한 문서의 완료 기준이 **여러 Workstream 에 걸쳐 있을 수 있다** —
   하나만 찾고 멈추면 나머지를 놓친다
5. **범위 제외 절(`Won't` · 제외 · 보류 · 다음 차수)을 반드시 읽는다.** 여기가 가장 자주
   빠지는 자리다. 다만 **제외를 충돌로 올리기 전에 한 가지를 먼저 확인한다** —
   **제외된 것과 요구된 것이 같은 대상인가.**

   | 확인 | 상태 |
   |---|---|
   | **같은 대상**인데 한쪽은 뺐고 다른 쪽은 그것을 전제로 삼는다 | **충돌** — 각자 진행하면 하나가 버려진다 |
   | 같은 **낱말**이지만 가리키는 것이 다르다 | **갭** — 용어 정의가 없다. 아래 "용어 중의성은 충돌이 아니라 갭이다" |
   | 양쪽이 같이 뺐다 | **정리됨** (제외 목록은 대체로 이쪽이다) |

   충돌인 예 — 상위 문서 전체가 SSR 전환을 전제하는데 화면 문서가 SSR 을 *"Won't — 다음
   차수"* 로 뺐다. 같은 SSR 이다. 갭인 예 — 제외 목록은 *"매출 리포트·데이터 분석"* 을 뺐고
   요건은 *"테이블 카드에 총 주문액 표시"* 를 요구한다. 둘 다 집계지만 **같은 것이 아니다.**

   **이 자리를 두 판 연속 틀렸다.** 같은 문서의 같은 절(제외 목록 §6)을 두 판 모두 충돌의
   한쪽으로 올렸고 두 판 모두 감점됐다. `contract_matrix.py` 가 **충돌의 근거가 범위 제외
   문장이면 표로 짚어 준다** — 그 표가 뜨면 위 세 줄로 다시 가른다
6. **한 문서 안에서 개요 절 · 상세 절 · 변경 이력을 서로 대조한다.** 위
   "한 문서 안의 모순도 Contract 가다" 참조
6-1. **제약 문장 목록을 만들고 쌍별로 대조한다.** 위 "제약 문장을 목록으로 먼저 뽑는다"
   참조. **이 단계를 건너뛰면 양립 불가를 통째로 놓친다** — 평가에서 5건이 그렇게 빠졌다
6-2. **ID 를 붙이기 전에 단위를 확인한다.** 후보 하나가 원문의 **번호·ID·표 행·불릿 여러 개**를
   담고 있으면 위 "Contract 하나의 단위" 로 가른다. **여기서 접으면 뒤에서 펼 수 없다** —
   Contract 수가 이후 모든 수치와 발견 하한 게이트의 입력이다
7. Contract 에 **ID를 붙인다**(C1, C2 …). 문서 전체에서 그 ID로만 부른다. 이름으로 부르면
   같은 Contract 를 두 이름으로 쓰게 된다

## Contract 마다 붙이는 네 가지

```
### C9. 루트 레이아웃 조립 — 셸 + Provider 이중성   🔴

**참여**: 004, 001, 003 · **결합 강도**: 상

| 문서 | 주장 |
|---|---|
| `004 §4` | "컨텍스트 주입은 WS2의 Provider" 라고 명시 |
| `001 축1` | 자기 `<FoCommonProvider>` 가 최상단 |

**충돌**: Provider 가 둘이다. 같은 것인지, 중첩인지, 하나가 다른 하나를 흡수하는지
아무 문서도 말하지 않는다.
**확정 대상**: Provider 개수와 중첩 순서, 각 Provider 가 주입하는 필드 분담.
```

- **참여자** — 이 Contract 를 언급하거나 소유를 주장한 Workstream. 정책 문서는 참여로 세지만
  **Workstream 수치에는 넣지 않는다**(경계를 주장하지 않으므로)
- **결합 강도** — 최상 / 상 / 중. 판정 기준은 *"이게 틀리면 무엇이 무효가 되는가"* 다.
  방향 전체가 무효면 최상, 한 Workstream 의 설계가 무효면 상, 국소 재작업이면 중
- **상태** — 아래 4분류
- **근거 인용** — 어느 문서 어느 절이 그렇게 말했는가. **문서 이름 + 절 번호 + 원문**
- **확정 대상** — 무엇을 결정해야 닫히는가. 이것이 파트 5의 계약 구간 작업 목록이 된다.
  **이름만 적혀 있고 필드·규칙·값이 없으면 정리됨이 아니라 갭(규격 미정)이다** — 이름으로
  닫은 것으로 세면 그 Contract 가 파트 4 에서 사라지고 실제로는 construction 까지 밀린다

### 근거는 상태와 무관하게 적는다

평가에서 **네 산출물 전부가 같은 자리에서 감점됐다** — 충돌·중복에는 참여 문서와 원문을
적고 **갭·정리됨에는 ID 와 상태만** 적었다. 충돌은 두 주장을 나란히 놓아야 하니 자연히
인용이 붙지만, 갭은 *"아무도 말하지 않았다"* 라서 인용할 것이 없다고 느껴지는 탓이다.

**갭에도 근거가 있다.** 무엇을 읽고 없다고 판단했는지가 근거다.

| 상태 | 무엇을 인용하는가 | 최소 |
|---|---|---|
| **충돌** | 경합하는 **양쪽** 원문 | 2개 |
| **중복** | 각자 소유를 주장한 문장 | 1개 |
| **갭** | 그 자리를 **비워 둔 문장** — 요건은 있는데 수단이 없다고 보이는 절, 또는 "미정·TBD" 표기 | 1개 |
| **정리됨** | 위임한 쪽의 문장 또는 수락한 쪽의 문장 | 1개 |

**참여 문서도 상태 넷 모두에 적는다.** 표로 낼 때 열은
`| ID | 대상 | 참여 | 강도 | 무엇이 부딪힌다·없다 |` 이고 갭·정리됨 표에서 참여 열을 빼지
않는다. 골격(`assets/assessment-base.html`)의 `s31`·`s42` 주석에 같은 열 구성이 있다.
**단위를 상태마다 바꾸지 않는다** — 충돌만 Workstream 으로 적고 나머지를 문서·절로 적으면 같은 열이 두
뜻이 되고, 채점자가 그것을 새 감점 축으로 지적했다.

갭에 인용할 문장을 못 찾으면 그 Contract 는 **문서에서 나온 것이 아니라 우리가 떠올린 것**이다.
그럴 때는 우리 판단임을 밝히고 **확인 요청으로 옮긴다.**

**Contract 목록에서 지우지는 않는다.** 이 지시가 실제로 역효과를 낸 적이 있다 — 근거를 요구하니
Contract 를 **보수적으로 고르게** 되어, 한 집합은 미결을 정리됨으로 밀고(9→4) 다른 집합은 Contract
수를 줄였다(20→16). 그렇게 빠진 미결 3건이 다음 채점에서 그대로 감점됐다. 지우면 문서에서
사라지고 미결 수가 함께 줄어든다. **확인 요청은 개수에 남는다** — 그게 차이다.

**충돌로 올리는 것을 겁내지 않아도 된다.** 충돌을 2건에서 12건으로 늘린 산출물이 채점자
전수 대조에서 거짓 양성 0건을 받았고, 충돌이 35~45건으로 커진 판에서도 **집합당 1건**이었다.
원문에 두 값이 있으면 충돌로 올린다. 거짓 양성보다 **누락이 훨씬 자주 감점된다.**

**그 1건이 늘 같은 모양이다** — 낱말·수는 겹치는데 대상이 다른 것. 아래
"대상 일치 확인은 충돌 전체에 적용한다" 가 그것을 거른다. 개수를 줄이라는 뜻이 아니다.

## 상태 4분류 판정 기준

| 상태 | 판정 | 해소 방법 |
|---|---|---|
| **충돌** | 두 문서가 **서로 다른 것**을 말한다. 양립할 수 없다 | 하나를 버린다 — 사람이 결정 |
| **중복** | 두 문서가 **같은 것**을 각자 소유한다고 주장한다 | 소유자를 갈라 준다 |
| **갭** | 아무도 말하지 않았거나 **소유자가 없다** | 규격을 쓰거나 배정한다 |
| **정리됨** | 한쪽이 다른 쪽에 **명시적으로 위임**하고 상대가 수락했다 | 그대로 승계 |

### 정리됨에는 합의의 범위를 적는다

**위임·수락이 있어도 세부는 미결일 수 있다.** 평가에서 이것 때문에 두 항목을 놓쳤다 —
세션 라이프사이클(첫 주문~이용 완료)은 두 절이 합의했는데 **그 세션의 ID 를 누가 언제
만드는지**가 정해지지 않아 순환이 있었다. 산출물은 라이프사이클 합의만 보고 통째로
정리됨에 넣었고, 순환과 용어 혼용을 함께 놓쳤다.

정리됨으로 분류할 때 **무엇이 합의됐고 무엇이 남았는지** 한 줄로 나눈다.

```
### C11. 테이블 세션 라이프사이클   🟢 정리됨(범위 한정)

**참여**: REQ §3.2.3 · REQ 부록 A · **결합 강도**: 상
**합의된 것**: 세션의 시작·끝 정의 — 두 절이 일치
**남은 것**: 세션 ID 의 생성 주체·시점 → **C12 로 분리**
```

표로 묶을 때도 **참여 열을 빼지 않는다.**

```
| ID | Contract | 참여 (절 번호까지) | 합의된 것 | 남은 것 |
|----|------|-------------------|----------|--------|
| C11 | 테이블 세션 라이프사이클 | `REQ §3.2.3` · `REQ 부록 A` | 시작·끝 정의 일치 | 세션 ID 생성 주체 → C12 |
```

**이 참여 열을 빠뜨리는 것이 가장 자주 나는 실패다.** 평가에서 세 집합이 *"합의된 것 /
남은 것"* 형식을 새로 만들면서 참여 열을 함께 빠뜨렸고, 그중 둘이 그 자리에서만 감점됐다.
충돌 카드에는 참여를 적는데 정리됨 표에는 잊는다 — **예시를 따라 쓰기 때문**이므로 위
예시를 그대로 쓴다.

남은 것이 있으면 **Contract 를 쪼갠다.** 쪼개기 어려우면 정리됨 카드 안에 남은 것을 적고 계획의
계약 구간에 넣는다. **합의의 범위를 적지 않은 정리됨은 미결을 감추는 자리가 된다.**

**충돌과 중복을 혼동하지 않는다.** 둘 다 "두 문서가 같은 것을 다룬다" 지만, 중복은 **결론이
같고 소유자만 겹치는 것**이라 조직으로 해소된다. 충돌은 결론이 반대라 조직을 바꿔도 남는다.
이 구분이 파트 2에서 *"이 넷은 조직을 바꿔서 없앨 수 없다"* 라는 문장의 근거다.

**갭은 다시 둘로 갈린다.** 소유자만 정하면 되는 것(고아)과 규격을 써야 하는 것. 계획에서
전자는 이름 한 줄이고 후자는 작업이므로, 파트 5에서 다르게 다뤄야 한다.

**갭도 표로 낸다. ID 나열로 끝내지 않는다.**

```
| ID | Contract | 참여 (절 번호까지) | Workstream | 없는 것 | 누가 써야 하는가 |
|----|------|-------------------|------|--------|----------------|
| C14 | 쿠폰 다운로드 응답 규격 | `REQ01 §9` · `RE06 §3` | 규격 | 실패 코드·재시도 | 아키텍트 + 백엔드 |
| C19 | 앞단 라우팅 진입 계약 | `REQ02 §2` · `RE05 §1.3` · `PDF §5-2` | 고아 | 소유자 | 아키텍트 |
```

**갭이 참여 없이 Layer 도해의 ID 나열로만 등장한 산출물이 두 판 연속 감점됐다.** 마지막 판에서는
충돌·중복·정리됨·고아에는 참여를 절 번호까지 붙였는데 **갭 아홉 건만 본문 어디에도 참여가
없었다** — 한 건은 이름조차 없이 ID 로만 있었다. 도해에 ID 를 쓰는 것은 좋지만 **그것이
Contract 의 등장 자리를 대신하지 못한다.** 상태 넷 전부가 같은 형식으로 본문에 있어야 한다.

`scripts/check_numbers.py` 가 이 누락을 기계로 짚는다 — Contract ID 는 본문에 있는데 그 근처에
참여 문서가 없는 자리를 표로 낸다. 조립을 끝낸 뒤 반드시 돌린다.

### 충돌을 갭으로 흘려보내지 않는다

**가장 자주 나는 오분류다.** 평가에서 한 산출물이 충돌 4~6건을 갭으로 적었고, 그 결과
계약 구간에 사람이 결정해야 할 항목이 실제보다 적게 보였다.

가르는 기준은 하나다 — **양쪽이 이미 각자 값을 적었는가.**

| 문서 상태 | 올바른 분류 |
|---|---|
| A 는 `8단계`, B 는 `9단계` 라고 적었다 | **충돌** — 값이 둘 다 있다 |
| A 는 `TC-YYYYMMDD-NNN`, B 는 `TC-202606-031` 을 예시로 썼다 | **충돌** — 형식이 둘 다 있다 |
| 아무 문서도 형식을 적지 않았다 | **갭** |
| 한 문서가 *"인셉션에서 정한다"* 로 미뤘다 | **갭** — 값이 없다 |
| A 는 자유 텍스트 입력, B 는 그 값으로 정형 집계 | **충돌** — 양립하지 않는다 |

**왜 갭 쪽으로 기울는가.** 갭은 *"정해지지 않았다"* 는 약한 주장이라 문장 하나로 끝난다.
충돌은 *"두 주장이 부딪힌다"* 는 강한 주장이라 **원문 두 개를 찾아 와야 한다.** 그 비용이
분류를 갭으로 밀어낸다. 갭으로 적어 둔 Contract 마다 **문서에 값이 이미 있는지** 되짚는다.

이 되짚기는 **아래 "대상 일치 확인" 절의 판정 순서 1번과 같은 질문**이다. 그 절에 실측 8건과
되짚는 방법이 있다 — 여기서 한 문장으로 끝내지 않는다. 실측에서 이 한 문장이 뒤쪽의 구체적인
규칙에 밀려 **네 집합 전부에서 진성 충돌이 갭으로 내려갔다.**

`scripts/term_sweep.py` 의 `number`·`format` 축이 이 유형을 기계로 짚어 준다. 거기 나온
자리는 값이 둘 다 있다는 뜻이므로 **대체로 충돌이다.**

### 용어 중의성은 충돌이 아니라 갭이다

`term` 축이 짚는 것은 다른 유형이다. **같은 낱말이 두 문서에서 다른 대상을 가리키는 것은
경합이 아니다** — 두 문서가 다른 값을 주장하는 게 아니라 같은 말을 다르게 쓰는 것이고,
**정의를 정리하면 사라진다.** 상태는 **갭(정의 누락)** 이 맞다.

| 원문 상태 | 분류 |
|---|---|
| 제외 목록은 *"분석 대시보드"* 를, 본문은 모니터링 그리드를 '대시보드' 로 부른다 | **갭** — 용어 정의가 없다 |
| 한쪽은 `8단계`, 다른 쪽은 `9단계` 라고 적었다 | **충돌** — 값이 경합한다 |

평가에서 이것을 충돌로 올린 산출물이 *"제외 항목을 충돌로 만들지 않았다"* 는 채점 항목에서
감점됐다. **짚는 것과 분류는 다른 일이다** — 용어 중의성을 갭으로 올려도 "짚었다" 는 요구는
충족된다.

**다음 판에서 같은 자리를 또 틀렸다.** 위 규칙 5(*"뺀 것이 다른 Workstream 의 전제이면 충돌"*)를
근거로 삼아 제외 절을 충돌의 한쪽으로 올렸다. 두 규칙이 부딪히는 자리이므로 **순서를
고정한다 — 같은 대상인지 먼저 보고, 같은 낱말일 뿐이면 갭이다.** 규칙 5 의 표가 그 순서다.
산출물이 파트 1 에 *"제외 목록은 경계를 주장하지 않는다"* 라고 적어 놓고 파트 2 에서 어긴
적이 있으니, **자기가 쓴 원칙과 분류가 맞는지 조립 뒤에 한 번 대조한다.**

**그 대조를 8단계 뒤에 다시 한다 — 「조립 뒤 한 번」으로는 신설분이 빠진다.** 실측에서 오분류
둘과 거짓 양성 하나가 **전부 8단계 이후에 새로 만든 Contract** 였고 셋 다 이 유형이다. 가장
강한 자리는 **같은 산출물의 파트 6 이** *"A 가 말하는 X 는 모킹 뼈대이고 B 의 Y 는 현행
게이트웨이다"* 로 **두 대상이 다르다고 스스로 판정했는데도** 그 Contract 가 최상 강도 충돌로
남은 것이다 — **대조 대상이 원문이 아니라 우리 문서 안에 있었다.** 다른 하나는 제목 자체가
*"한 식별자가 같은 절에서 두 대상을 가리킨다"* 로 **이 절의 발동 문장**인데 충돌이었다.
→ 신설·수정한 Contract 는 **핵심 낱말로 산출물 전체를 `grep` 해** 다른 절이 이미 다른 판정을
말하는지 보고, 말하고 있으면 **둘 중 하나를 지금 고른다.** 양쪽을 남기면 논리 모순이 된다.

### 대상 일치 확인은 충돌 전체에 적용한다

위 순서를 제외 목록에만 쓰면 부족하다. **충돌을 많이 찾은 판에서 거짓 양성이 집합당 1건씩
나왔고, 네 건 전부 같은 모양이었다** — 낱말이나 수는 겹치는데 **대상이 다르다.** 인용 양쪽이
원문에 실재해도 거짓 양성이다. 어긋나는 축이 넷이다.

| 축 | 실측 |
|---|---|
| **화면·기능이 다르다** | *"300행/페이지"* 는 원문이 *"TC 관리 페이지 기본 조회 단위"* 로 못 박았고 *"20개씩 보기"* 는 Cycle 실행 그리드였다 |
| **as-is / to-be 가 다르다** | to-be 컴포넌트의 배선 부재와 *"현행 타임아웃 실측값"* 을 맞붙였다. 백엔드에 API 가 있고 to-be 가 안 붙은 것은 모순이 아니다 |
| **범위가 다르다** | 제외 목록의 대상은 기존 프로젝트 **전체** 라우팅이고 결정문의 대상은 **신규 존** 규약이었다 |
| **산출물 계열이 다르다** | 앱 탭 *"3종"* 과 인쇄 분석지 *"3종"* — 같은 수가 겹쳤을 뿐이다 |

**막는 방법은 인용을 자르는 자리에 있다.** 네 건 모두 원문에 대상을 못 박은 수식어가 있었고
산출물이 **그것을 떼고 인용했다.** 그래서 규칙은 이렇다.

> **인용에 대상 수식어를 함께 가져온다.** *"기본 조회 단위"* · *"현행 … 실측값"* · *"신규 존"*
> 같은 한정어를 지우지 않는다. 양쪽 인용을 나란히 놓았을 때 **한정어가 서로 다른 것을
> 가리키면 충돌이 아니다** — 대체로 갭(정의·매핑 누락)이고, 진성 쟁점은 다른 Contract 가 이미
> 담고 있다.

두 인용을 붙여 놓고 *"이 둘이 같은 대상을 말하는가"* 를 소리 내어 확인한다. 낱말이 같다는
것은 근거가 아니다.

#### 갭으로 내릴 때마다 반대 질문을 한다 — 이 확인은 양방향이다

**위 규칙만 걸었더니 반대쪽으로 넘쳤다.** 거짓 양성은 집합당 1건에서 0~1건으로 줄었는데
**진성 충돌이 갭으로 내려간 것이 네 집합 전부에서 8건** 나왔고 충돌 수가 반으로 줄었다
(35→16 · 38→18). 산출물들이 본문에 *"양쪽이 값을 적었으면 충돌"* 이라고 스스로 적어 놓고
그 기준을 어겼다.

그래서 **대상이 다르다고 판단해 갭으로 내리는 순간 곧바로 되묻는다.**

> **양쪽이 이미 각자 값을 적었는가?** 적혀 있으면 대상 판단과 **무관하게 충돌이다.**
> 대상 일치 확인은 *"같은 낱말이 다른 것을 가리키는 경우"* 를 걸러내는 장치이고,
> **양쪽에 값이 있는 경우를 갭으로 내리는 장치가 아니다.**

실측에서 내려간 것들이다.

| 자리 | 왜 충돌인가 |
|---|---|
| **쌍둥이가 갈렸다** | `C38`(유효상품 0개 비노출)과 `C41`(위탁계약 필터)이 **`C37`·`C42` 와 같은 절·같은 문장 구조**인데 상태만 달랐다. *"~해야 한다"* ↔ *"API 의존, FE 필터 없음"* 은 양쪽에 값이 있다 |
| Contract 제목이 이미 말한다 | `C92` 는 제목이 *"어긋난다"* 인데 상태가 갭이었다(12레벨 노출 ↔ 완료 레벨 ±1단계만) |
| 최상 강도인데 갭 | `C42` 요건서 §2 에 환경 필드가 없다 ↔ M3화면 §6.2 는 TC 행에 환경 태그를 그린다 |
| 채점 항목이 충돌로 부른다 | `C40` Plan 단위 독립 ↔ 단일 상태 표시 |
| 스스로 결정이라 적고 갭 | `C63` *"녹음파일 최대 2개"* ↔ *"미션수행 횟수 제한 없음"* — 산출물이 *"아키텍트가 고르는 결정"* 이라 쓰고도 갭으로 뒀다 |

**두 축을 같은 순서로 매번 통과시킨다.**

1. 양쪽에 값이 **둘 다** 있는가 → 있으면 **충돌.** 여기서 멈춘다
2. 없으면(한쪽만 값이 있거나 아무도 없다) → 대상 일치를 본다. 같은 낱말이 다른 것을
   가리키면 **갭(정의 누락)**
3. 둘 다 아니면 갭이다

**"판단이 서지 않으면 갭" 은 1번을 통과한 뒤에만 쓴다.** 갭은 정의를 요구하고 충돌은 결정을
요구하므로 없는 결정을 요구하는 것이 비싼 실수인데, **있는 결정을 정의 문제로 내려보내는 것도
같은 무게의 실수다** — 계약 구간에 사람이 결정할 항목이 실제보다 적게 보인다.

조립을 끝낸 뒤 **갭 전량을 한 번 되짚는다.** 위 1번만 다시 묻는 일이라 빠르다. 실측에서
`notes.md` 에 *"갭을 다시 봤고 양쪽에 값이 적힌 것은 없다"* 고 적고 틀린 산출물이 있었으므로,
되짚었다는 문장 대신 **되짚은 목록을 남긴다.**

#### 되짚기도 양방향이다 — 갭만 되짚으면 반대쪽이 쌓인다

**위 문단을 갭에만 걸었더니 반대 방향이 통째로 남았다.** 한 런이 스스로 적었다 —
*"되짚기를 갭→충돌 한 방향으로만 걸어 반대 방향(충돌→갭) 오분류 8건을 통째로 놓쳤다."*
같은 판에서 다른 집합의 오분류 4건도 **전부 갭→충돌 한 방향**이었다. 독립 검토자는 양방향으로
낸다(충돌→갭 16 · 갭→충돌 5) — **기우는 것은 우리 쪽 되짚기다.**

**그래서 되짚기를 두 번 돌린다.**

| 되짚는 대상 | 묻는 것 | 옮기는 방향 |
|---|---|---|
| **갭 전량** | 양쪽에 값이 **둘 다** 있는가 | 있으면 → **충돌** |
| **충돌 전량** | 두 인용이 **같은 대상**을 말하는가 | 아니면 → **갭**(같은 낱말·다른 대상) |

충돌 쪽 되짚기는 위 "대상 일치 확인" 의 판정 순서 2번을 충돌 전량에 다시 대는 일이다.
`term_sweep.py` 의 `term` 축 후보와 겹치는 자리를 먼저 본다 — 그 축이 짚는 것이 정확히
*"같은 낱말·다른 대상"* 이다.

**두 목록을 따로 남긴다** — `notes.md` 에 `되짚기 A: 갭 N건(ID 열거) → 옮긴 것 M건(ID 열거)` ·
`되짚기 B: 충돌 N건(ID 열거) → 옮긴 것 M건(ID 열거)`. 한쪽 목록만 있으면 그 판은 한 방향으로
걸린 것이다.

**수만 적지 않는다 — 괄호에 ID 를 열거한다.** *"목록을 남긴다"* 고 하면서 수만 적으면 그것은
목록이 아니고, 실측에서 **그렇게 적은 수가 틀렸다**(*"채택 8 / 기각 17"* ↔ 실측 7/18).
열거가 붙으면 **수의 정본이 그 열거**가 되고 `check_numbers.py` 의 *"괄호 안 ID 열거가 그 수와
1:1 인가"* 검사가 그 자리를 받는다. 원소가 스무 개를 넘으면 열거하지 말고 **그 표를 가리킨다.**

## 고아 판별

**수단을 제공하는 쪽과 요건을 가진 쪽이 서로를 참조하지 않는 것.** 전형적인 모양이다.

- A 문서: 전달 수단을 제공한다고 적었다 (예: 이벤트 싱크 인터페이스)
- B 문서: 요건을 갖고 있다 (예: 추적 도구 세 종의 패리티)
- 두 문서가 서로를 언급하지 않는다. 나머지 문서는 인수 목록에서 제외했거나 언급이 없다

**두 번 만들거나 아무도 만들지 않는다.** 이 한 줄이 산출물의 `s33` 머리에 들어간다 —
독자에게 고아를 설명하는 문구이고, 정의 자리는 SKILL.md 7단계 *"우리 낱말을 독자 말로
정의한다"* 에 표로 있다. 그래서 배정이 계획의 진입 조건이 된다 — 소유자
없는 항목이 남아 있으면 다음 단계로 넘어갈 때 걸린다. 그것은 결함이 아니라 **배정을
강제하는 장치**이므로 그렇게 적는다.

## Contract 카드 형식

HTML 에서는 `.surface` 카드로 그린다. 상태에 따라 왼쪽 테두리 색이 갈린다
(`.surface.con` / `.dup` / `.gap` / `.ok`). 카드 안에 `.sfv` 블록으로 충돌 내용과 확정
대상을 넣는다.

**22개를 전부 카드로 그리지 않는다.** 충돌은 카드로, 고아는 `.cards c2` 로, 나머지는 표로
묶는다. 카드가 스무 장 넘어가면 읽는 사람이 중요한 것을 못 찾는다.

### 충돌 전량에 양쪽 원문을 넣는다 — 카드가 아니어도 된다

위 두 지시가 부딪히는 자리가 있다. **충돌이 많으면 카드를 다 만들 수 없다.** 평가에서
충돌 12건 중 4건에 카드가 없어 양쪽 인용이 빠졌고, 문서가 스스로 *"상 8건을 카드로 제시"*
라고 적었는데 그중 하나가 누락돼 **내부 주장과도 어긋났다.**

가르는 기준은 이렇다.

| | 형식 | 원문 인용 |
|---|---|---|
| 결합 강도 **최상·상** 충돌 | `.surface` 카드 | 양쪽 |
| 결합 강도 **중** 충돌 | **양쪽 인용 표** | 양쪽 |
| 중복·갭·정리됨 | 요약 표 (참여·근거 열) | 1개 |

**충돌은 강도와 무관하게 양쪽 원문이 있어야 한다** — 카드일 필요는 없다. 양쪽 인용 표는
이런 모양이다.

```
| ID | Contract | `문서 A` 주장 | `문서 B` 주장 | 확정 대상 |
|----|------|--------------|--------------|----------|
| C9 | 결함 상태 단계 수 | `REQ §4.1` "8단계 상태 관리 Flow" | `REQ FR-M3-04-4` "9단계 Flow" 표 | 단계 수와 각 단계의 이름 |
```

카드 수를 세어 본문에 적었으면 **그 수와 실제 카드 수가 같은지 확인한다.** 표지 수치와
같은 종류의 어긋남이고, `contract_matrix.py` 가 잡아 주지 않는다.

**표로 묶어도 참여 문서와 근거 절은 남긴다.** 네 산출물이 전부 이 자리에서 감점됐다 —
카드로 그린 충돌에는 참여와 원문이 붙었지만, 표로 묶은 갭·정리됨에는 **ID 와 상태만** 남아
어느 문서가 당사자인지 사라졌다. 요약 표의 최소 열은 넷이다.

```
| ID | Contract | 참여 (절 번호까지) | 상태 | 근거 |
|----|------|-------------------|------|------|
| C7 | 에러 404 경계 | `004 §4-2` · `003 §6` | 정리됨 | "소유자를 정해야 한다" → notFound boundary 로 연결 |
```

`contracts.json` 의 `cites` 를 그대로 옮기면 이 열이 채워진다. 분석 파일에만 있고 HTML 에
없으면 **없는 것으로 채점된다** — 고객이 읽는 것은 HTML 뿐이다.

## 미결 안건 형식 — 결론을 쓰지 않는다

Contract 를 문서 밖으로(예: AI 에이전트가 읽는 지식 계층) 옮길 때는 형식을 이렇게 고정한다.

```
## C9 · 루트 레이아웃 조립 — 셸 + Provider 이중성    상태: OPEN
결정 단계: contract-design
당사자: 004 · 001 · 003
경합 주장 (어느 것도 확정 아님)
  004 §4  : "컨텍스트 주입은 WS2의 Provider"
  001 축1 : "<FoCommonProvider> 가 최상단"
미확정: 같은 Provider 인가 / 중첩인가 / 컨텍스트 출처
원문 대조: <원문 경로>
```

**규칙 세 개.**

1. 결론을 쓰지 않는다. 상태는 `OPEN` 이고 어느 주장에도 확정·채택 표시를 붙이지 않는다
2. 경합 주장은 **양쪽을 원문 그대로** 인용하고 출처를 절 번호까지 붙인다
3. 항목마다 **상태 · 결정 단계 · 당사자 · 원문 대조 경로**만 더한다

이 형식을 지키는 이유는 규칙 계층과 지식 계층의 성격이 다르기 때문이다. 규칙 계층은
*"다시 묻지 않는 결정"* 을 담는 자리라, 미확정 주장을 여기 올리면 한쪽이 사전 비준된다.
지식 계층은 그 구속이 없으면서도 자동으로 읽히므로, 의제를 놓치지 않게 하면서 편향을
만들지 않는다.
